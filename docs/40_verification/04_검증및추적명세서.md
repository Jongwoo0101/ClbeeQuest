# 04. TUK-Shell 검증및추적명세서

> **기준 문서**: `docs/plan.md`
> **목적**: 계획서, 기능 명세, 인터페이스 명세, 파이프라인 명세 사이의 추적성과 검증 기준을 정의

---

## 1. 문서 추가 이유

기존 3개 명세서는 기능 설명은 가능하지만 다음 항목이 부족했다.

- `plan.md`의 1~7단계가 어떤 문서와 테스트로 검증되는지 직접 연결되지 않음
- 팀원별 책임과 연동 완료 기준이 문서 단위로 흩어져 있음
- 구현 후 "무엇이 완료되면 단계가 끝나는가"에 대한 판정 기준이 없음

본 문서는 위 세 문제를 보완하기 위해 추가한다.

## 3. 단계별 완료 기준

### 3-1. 1단계: 기본 REPL 루프

- `TUK-OS > ` 프롬프트가 반복 출력된다.
- 외부 명령 `ls`, `pwd` 수준의 실행이 가능하다.
- 포그라운드 명령 실행 후 다시 입력 대기로 복귀한다.

### 3-2. 2단계: 구조체 + 연결 리스트

- `sleep 10 &` 실행 시 작업이 리스트에 등록된다.
- 등록 시 PID, 명령어, 시작 시각이 저장된다.
- 종료 확인 후 노드가 제거된다.

### 3-3. 3단계: `jobs` 검색

- `jobs`가 전체 목록을 표 형식으로 출력한다.
- `jobs -pid PID`가 정확히 1개 또는 0개를 반환한다.
- `jobs -name KEYWORD`가 부분 문자열 기준으로 동작한다.

### 3-4. 4단계: `top` 정렬

- `top -cpu`, `top -mem`, `top -time`가 서로 다른 기준으로 정렬된다.
- 정렬은 원본 리스트를 깨뜨리지 않는다.

### 3-5. 5단계: `/proc` 연동

- 실행 중 프로세스의 CPU/메모리 값이 갱신된다.
- `/proc` 접근 실패가 쉘 전체 종료로 이어지지 않는다.

### 3-6. 6단계: 히스토리 파일 입출력

- 명령 실행 후 `.tuk_history`에 기록된다.
- 쉘 재시작 시 이전 기록이 로드된다.

### 3-7. 7단계: 캠퍼스 특화 명령어

- 각 명령어의 옵션 검증이 동작한다.
- 더미 데이터 기반 출력 또는 핸들러 호출까지 연결된다.

## 4. 역할별 검증 포인트

| 담당자 | 환경 | 핵심 검증 항목 |
|--------|------|----------------|
| 이우진 | Bash | REPL, built-in, `jobs`, `top`, history |
| 원종우 | Zsh | 캠퍼스 명령 핸들러, 데이터 출력 |
| 동현 | PowerShell + WSL | `/proc` 파싱, 프로세스 상태 갱신 |

- 공통 구조체와 함수 시그니처가 먼저 고정되어야 병렬 구현이 가능하다.
- 플랫폼별 차이는 호스트 쉘에만 존재하고, TUK-Shell 내부 명령 형식은 바뀌면 안 된다.

## 5. 최소 테스트 시나리오

| ID | 시나리오 | 기대 결과 |
|----|----------|-----------|
| T01 | `pwd` | 현재 경로 출력 |
| T02 | `cd ..` 후 `pwd` | 상위 디렉토리로 변경 확인 |
| T03 | `sleep 3 &` | 백그라운드 등록 메시지 출력 |
| T04 | `jobs` | 등록된 `sleep` 작업 표시 |
| T05 | `jobs -pid <pid>` | 해당 작업 1건 조회 |
| T06 | `jobs -name sleep` | 부분 문자열 검색 성공 |
| T07 | `top -time` | 실행시간 기준 정렬 출력 |
| T08 | 쉘 종료 후 재실행 | `.tuk_history` 로드 확인 |
| T09 | `notice -a -n 3` | 옵션 조합 파싱 성공 |
| T10 | 잘못된 옵션 입력 | 사용법 또는 오류 메시지 출력 |

## 6. 문서 사용 순서

1. `docs/plan.md`로 전체 목표와 단계 확인
2. `01_상세기능명세서.md`로 기능 요구사항 확인
3. `02_인터페이스명세서.md`로 함수/CLI/파일 인터페이스 고정
4. `03_파이프라인명세서.md`로 실행 순서와 자원 회수 시점 확인
5. `04_검증및추적명세서.md`로 단계 완료 판정 및 테스트 수행

---

## 7. 결론

이 문서를 기준으로 하면 `plan.md`의 요구사항이 기능, 인터페이스, 실행 흐름, 검증 기준으로 분리되어 추적 가능해진다. 구현 전에 팀 간 함수 시그니처와 옵션 규칙을 먼저 확정하고, 이후 단계별로 테스트를 통과시키는 방식으로 진행한다.
